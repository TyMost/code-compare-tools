# 多仓库异步任务优化方案

## 1. 背景概述
- 现有 Git 增量扫描与 diff 生成链路为同步阻塞模式，大型仓库会导致接口超时（前端 Axios 15s）。
- 随着多仓库并行接入，刷新请求频次与数据量将显著增加，现有模型存在性能、稳定性与用户体验风险。
- 目标是在 JDK 8 / Spring Boot 体系内，引入可扩展的异步任务框架，支持多仓库扫描、差异生成及结果查询。

## 2. 目标与范围
### 2.1 主要目标
- 将「扫描 + diff 生成」改造为后台异步任务，HTTP 接口快速返回任务 ID。
- 支持多仓库并发调度、任务排队与状态追踪。
- 前端通过轮询/订阅获取任务进度与结果，避免页面阻塞超时。
- 具备任务持久化、失败恢复与监控告警能力。

### 2.2 范围界定
- 后端：扫描服务、事件监听器、REST API、任务存储、调度线程池。
- 前端：Git 比对视图与 Dashboard 刷新逻辑的任务化改造。
- 基础设施：数据库或 Redis 存储任务状态，新增监控指标。
- 暂不涉及：diff 算法本身、规则模板等业务逻辑调整。

## 3. 总体架构设计
### 3.1 流程概览（文字描述）
1. 用户在前端发起刷新或批量扫描请求。
2. 后端接收请求，校验参数，写入任务表/队列，并返回 `202 Accepted + jobId`。
3. 后台任务执行器按并发策略取出任务，执行 Git 拉取、增量扫描、diff 生成、汇总持久化。
4. 执行过程中持续更新任务状态、进度、耗时与输出。
5. 前端轮询 `/jobs/{id}` 或订阅推送通道，展示进度、完成结果或失败原因。
6. 任务完成后，原有查询接口（如 `/migration/git-comparison`）可直接读取最新结果。

### 3.2 组件划分
- **任务提交 API 层**：负责请求校验、去重、生成 jobId、写入持久层。
- **任务调度器**：基于 Spring `TaskExecutor` 或自建 `ExecutorService`，控制并发队列。
- **任务执行器**：封装现有 `FileScanService.scanIncremental` 与 `ProjectDiffGenerator`，支持阶段化执行与进度上报。
- **任务存储层**：数据库表 / Redis，用于任务状态、元数据、输出引用的持久化。
- **前端任务管理模块**：维护 job 列表、轮询、错误提示与结果展示。
- **监控告警模块**：导出任务数、排队时长、失败率、执行耗时等指标。

## 4. 后端改造方案
### 4.1 任务模型设计
- 新增实体 `ScanJob`：
  - `id`（UUID）、`projectCode`、`sourceProjectKey`/`targetProjectKey`。
  - `type`（单仓库刷新、对仓比对、批量任务等）。
  - `status`（PENDING、RUNNING、SUCCEEDED、FAILED、CANCELLED）。
  - `progress`（0~100，保留两位小数）。
  - `queuedAt`、`startedAt`、`completedAt`、`durationMs`。
  - `resultRef`（指向最新 summary / diff 的标识）、`message`（失败原因）。
  - `payload`（JSON，记录扫描参数、分组信息）。
- 状态流转：
  - 提交：PENDING。
  - 调度取出：RUNNING。
  - 完成：SUCCEEDED/FAILED。
  - 手工取消：CANCELLED。

### 4.2 任务调度器与执行
- 使用 Spring `ThreadPoolTaskExecutor`（JDK 8 可用）：
  - `corePoolSize` 基于 CPU（建议：N 核服务器 `N`~`2N`）。
  - `maxPoolSize`、`queueCapacity` 控制同批次排队。
  - 自定义 `RejectedExecutionHandler`，在队列满时返回错误或延迟。
- 支持多实例部署时的分布式调度：
  - 方案 A：数据库基于 `SELECT ... FOR UPDATE` / 乐观锁抢占任务。
  - 方案 B：Redis `SETNX` / Redisson公平锁。
  - 方案 C：引入消息队列（如 RabbitMQ），任务由 MQ 广播到执行节点。
- 执行流程拆分：
  1. Git 引用同步（可选 fetch）。
  2. `FileScanService.scanIncremental(request, persistFlag)`。
  3. `ProjectDiffGenerator` 触发 diff、snapshot 与统计。
  4. 更新 `ScanJob` 进度（里程碑式 0%、10%、50%、80%、100%）。
  5. 错误捕获并写入任务记录。
- 对 `ScanCompletedEvent` 的 Listener 改造：
  - 通过任务上下文传播到监听器，避免重复触发。
  - 考虑 `ProjectDiffGenerator` 内部也改用异步，以防任务线程阻塞。

### 4.3 API 调整
- 新增：
  - `POST /api/v1/migration/scan-jobs`：提交单仓库刷新。
  - `POST /api/v1/migration/git-comparison/jobs`：提交源/目标对比刷新。
  - `GET /api/v1/migration/scan-jobs/{jobId}`：查询任务状态。
  - `GET /api/v1/migration/scan-jobs?projectCode=...`：历史任务列表（分页）。
  - （可选）`DELETE /api/v1/migration/scan-jobs/{jobId}`：取消未执行或运行中任务。
- 兼容老接口：
  - `/migration/git-comparison` 接口保留，但前端应仅在任务成功后调用获取结果。
  - `/migration/overview` 亦同。
- 响应示例：
  ```json
  POST /scan-jobs
  {
    "jobId": "c1a2...",
    "status": "PENDING",
    "estimatedStartDelayMs": 3500
  }
  ```

### 4.4 数据存储与表结构
- `scan_job` 表建议结构（MySQL 为例）：
  | 字段 | 类型 | 说明 |
  | --- | --- | --- |
  | id | varchar(64) PK | jobId |
  | job_type | varchar(32) | SCAN / COMPARISON / BATCH |
  | project_code | varchar(128) | 主项目/对比 ID |
  | payload | text/json | 参数 |
  | status | varchar(16) | 枚举 |
  | progress | decimal(5,2) | 0~100 |
  | queued_at | timestamp | |
  | started_at | timestamp | |
  | completed_at | timestamp | |
  | duration_ms | bigint | |
  | result_ref | varchar(255) | 指向 summary/diff |
  | message | text | 错误信息 |
  | created_by | varchar(64) | 操作者/系统 |
  | updated_at | timestamp | 更新时间 |
- 索引：`status`、`project_code+status`、`queued_at`。
- 可选 Redis 缓存：加速查询最新任务、并发控制。

### 4.5 并发与限流策略
- 同仓库互斥：提交前检查是否存在 `status in (PENDING, RUNNING)` 的同类任务，选择复用或拒绝。
- 全局并发：线程池最大并发 + 数据库/Redis 中的分布式信号量控制。
- 批量任务：支持将多仓库任务拆成子任务，统一归属父 jobId，统计整体进度（完成子任务/总任务）。
- 资源监控：监测 Git 拉取、diff 生成耗时，必要时按仓库大小设置优先级或分层队列。

### 4.6 错误处理与重试
- 分类错误：可重试（网络抖动、Git fetch 失败）、不可重试（配置缺失、路径不存在）。
- 任务状态字段记录失败原因，前端展示友好提示。
- 手工重试 API：`POST /scan-jobs/{jobId}/retry`。
- 自动重试政策：可配置最大重试次数、退避策略。

## 5. 前端改造方案
- Vuex 新增 `jobs` 模块：
  - `state`: job 列表、当前 job 详情、轮询定时器 ID。
  - `actions`: `startJob`, `pollJobStatus`, `stopPolling`, `loadJobHistory` 等。
- 提交操作流程：
  1. 点击刷新 → 调用 `startJob` → 接口返回 jobId。
  2. 根据 jobId 定时（例如 2s）调用查询 API。
  3. 根据状态更新 UI：排队、进行中、成功、失败。
  4. 成功后触发原有数据刷新；失败则提示并允许重试。
- 批量扫描界面需支持展示多条任务进度，提供过滤（仅当前项目/全部）。
- Axios 超时可适当降低（如 10s），避免长轮询占用线程；轮询接口特殊处理，失败后退避重试。
- 可选：当任务数量多时，通过 WebSocket/SSE 推送状态，降低轮询压力。

## 6. 配置与部署
- `application.yml` 扩展配置：
  ```yaml
  migration:
    job:
      executor:
        core-size: 4
        max-size: 8
        queue-capacity: 50
      retry:
        max-attempts: 2
        backoff-ms: 5000
      polling:
        ttl-hours: 24
  ```
- 生产环境需确保数据库/Redis 连接池容量满足任务频次。
- 灰度策略：先在预生产开启异步模式，验证性能后再切换正式环境。

## 7. 监控与告警
- 指标建议（Prometheus/Grafana）：
  - `scan_job_queue_size`、`scan_job_running_count`、`scan_job_duration_ms`。
  - 按仓库维度：成功率、平均耗时、失败原因分布。
  - 前端：轮询失败率、任务完成耗时分布。
- 告警阈值：
  - 排队时长 > 5 min。
  - 任务失败率 > 5%。
  - 单任务执行时间 > 30 min。

## 8. 迁移实施计划
1. **技术方案评审**：确认模型、接口、线程池、数据表设计。
2. **后端基础建设**：实现任务模型、DAO、调度器、状态更新、API。
3. **扫描 & diff 协调**：调整现有服务调用链，确保任务上下文可传递。
4. **前端改造**：开发 job 模块、轮询逻辑、UI 状态展示。
5. **联调测试**：覆盖单仓库、多仓库、失败重试、取消等场景。
6. **迁移切换**：
   - 阶段 1：保留同步接口+异步实验接口。
   - 阶段 2：前端切换到异步接口，旧接口废弃。
   - 阶段 3：压测与监控校验，发布正式环境。
7. **文档与培训**：更新运维手册、接口文档、故障处理流程。

## 9. 风险与应对
- **任务堆积**：大批量仓库同时触发导致排队过长 → 需实现优先级/限流与告警。
- **状态一致性**：任务完成但状态未更新 → 采用事务或最终一致性补偿（定时扫描过期 RUNNING）。
- **失败重试频繁**：重复失败导致资源浪费 → 动态调整重试策略，分析失败根因。
- **多实例竞争**：重复执行同一任务 → 分布式锁 / 调度协调。
- **前端体验**：轮询带来的流量和耗电 → 可视需求引入推送机制。

## 10. 后续扩展方向
- **任务分类扩展**：支持规则刷新、AI 生成等其他耗时操作共用任务框架。
- **动态调度**：根据仓库大小、历史耗时自动分配优先级与资源。
- **分布式执行**：将扫描/diff 拆分到独立服务或容器，支持弹性扩容。
- **可视化看板**：构建任务监控大屏，展示多仓库同步状态。
- **审计与追踪**：记录操作人、请求来源、版本信息，便于追踪问题。

---
本方案旨在为多仓库场景下的扫描与 diff 工作流提供可靠的异步化基础。后续实施应结合实际部署架构、仓库规模与团队运维能力，逐步落地并持续优化。
