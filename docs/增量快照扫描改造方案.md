# 增量快照扫描改造方案

## 背景
当前后端的“时间区间模式”仅针对单一 `refHint`（通常是 `branchFrom/branchTo` 或 `HEAD`）执行 RevWalk，找到窗口内的最早/最晚提交，再用 `GitRepoScanner` 生成一次 diff。虽然已经是“起止快照”的雏形，但无法覆盖 **全仓库所有分支**，且定位/组装逻辑分散，不便复用。

## 改造目标
1. **全仓库范围**：对仓库中所有目标引用（默认 `refs/heads/*`，可配置是否包含远端 / tag）执行时间扫描，找到全局 `earliestCommit` 与 `latestCommit`。
2. **模块化**：引入 SnapshotLocator / SnapshotDiffExtractor / IncrementalSnapshotAssembler / IncrementalSnapshotScanner，形成清晰的管线。
3. **性能**：RevWalk 在每个分支上只遍历所需提交（按时间剪枝），生成差异仅一次 diff。
4. **兼容**：保留现有 diff 输出结构（`DiffSummary`/`DiffFile`），新增 facade 供 Scan 流程调用。

## 模块设计
### 1. SnapshotLocator
- **职责**：扫描指定仓库的全部引用，结合 `startTime`/`endTime` 找到全局最早/最晚提交。
- **输入**：`Repository repository`, `Instant startTime`, `Instant endTime`, `SnapshotLocatorOptions`（如 ref 匹配规则、最大分支数、防御性限制）。
- **算法**：
  1. 枚举 `refs/heads/*`（必要时包含 `refs/remotes/*`），支持通过配置过滤。
  2. 对每个 ref 使用 `RevWalk`，排序方式 `RevSort.COMMIT_TIME_DESC`。
  3. 遍历时若 `commitTime > endTime` 继续；若 `commitTime < startTime` 且当前遍历目标是 EARLIEST 则 `break`。
  4. 维护两个全局变量：`earliestCandidate`（最接近 `startTime` 的最早提交）和 `latestCandidate`（不晚于 `endTime` 的最新提交）。
  5. 返回二者（若任何一个缺失需明确错误提示）。
- **产出**：`SnapshotPair { RevCommit earliest, RevCommit latest }`

### 2. SnapshotDiffExtractor
- **职责**：对 `earliestCommit.getTree()` 与 `latestCommit.getTree()` 做一次 diff。
- **实现**：
  - 复用现有 `GitRepoScanner` 中的 `DiffFormatter` 初始化逻辑：
    - `DiffFormatter formatter = new DiffFormatter(DisabledOutputStream.INSTANCE)`
    - `formatter.setRepository(repository)`
    - `formatter.setDiffComparator(RawTextComparator.DEFAULT)`
    - `formatter.setDetectRenames(true)`
  - 调用 `formatter.scan(treeA, treeB)`，返回 `List<DiffEntry>`。

### 3. IncrementalSnapshotAssembler
- **职责**：将 `DiffEntry` 列表转换成项目内部需要的结构（如 `DiffFile`/`DiffBlock` / 或者新的轻量 DTO）。
- **策略**：
  - 可复用 `GitDiffAdapter` 将 `DiffEntry` → `DiffFile`，减少重复代码。
  - 若需要更轻量的输出（`path/changeType/patch`），可新增 DTO 并在 adapter 中复用行级 patch 提取。

### 4. IncrementalSnapshotScanner
- **Facade**：提供 `scan(RepoConfig config, Instant startTime, Instant endTime)`。
- **流程**：
  1. 打开 `Repository`（沿用 `GitRepoScanner.openRepository`）。
  2. `SnapshotLocator.locate(repository, startTime, endTime)` → 得到 `SnapshotPair`。
  3. `SnapshotDiffExtractor.diff(repository, pair)` → 获取 `DiffEntry` 列表。
  4. `IncrementalSnapshotAssembler.assemble(diffEntries, repoConfig)` → 输出 `DiffSummary` 或自定义结构。
  5. 返回结果供 `DiffAppService` / `ScanAppService` 继续处理（覆盖率、迁移等逻辑保持不变）。

## 与现有逻辑的关系
| 模块 | 现状 | 改造 |
| --- | --- | --- |
| 提交定位 | `GitBranchFetcher` 中根据单个 `refHint` 解析 `ObjectId` | 重构/复用为 `SnapshotLocator`（可保留旧逻辑用于“按分支 diff”场景） |
| Diff 生成 | `GitRepoScanner` 直接扫描 base/target | 拆分成 `SnapshotDiffExtractor` + `IncrementalSnapshotAssembler`，以便新的 facade 使用 |
| Scan 流程 | `DiffAppService.generateDiff` → `ScanAppService.scan` | 当请求为“时间范围 + 全仓库”时调用 `IncrementalSnapshotScanner`，否则继续沿用现有分支模式 |

## 兼容策略
- `DiffRequestDTO`/`RepoConfig` 中新增布尔或枚举开关，例如 `scanStrategy=SNAPSHOT` / `BRANCH`，在 `ScanMapper` 中根据请求选择哪条逻辑。
- 允许配置“最大扫描分支数量”“包含的 ref pattern”，避免在大型仓库上过度遍历。
- 原先的单分支时间模式仍可复用 `GitBranchFetcher`（可能重命名为 `BranchSnapshotLocator`），供特定场景使用。

## 实施步骤
1. **引入新模块**：创建 `SnapshotLocator`, `SnapshotDiffExtractor`, `IncrementalSnapshotAssembler`, `IncrementalSnapshotScanner`。
2. **重构 GitRepoScanner**：将 repository 打开/关闭、DiffFormatter 初始化等工具方法抽取到新模块可复用的位置。
3. **Scan 流程接线**：在 `DiffAppService` 中判断 `RepoConfig.getScanStrategy()`；若为 SNAPSHOT，则调用新 facade，并返回与旧结构兼容的 `DiffSummary`。
4. **配置 & 文档**：在 `docs/backend/api`、`application.properties` 中描述如何启用新模式（如 `migratediff.scan.snapshot.enabled=true`），并提供示例请求。
5. **测试**：新增单元/集成测试覆盖：
   - 多分支仓库时间定位（`o`, `g`, `g-extra`）
   - 仅有部分分支命中窗口的场景
   - Diff 结果与 `git diff <earliest> <latest>` 对齐

## 风险与应对
- **性能**：遍历所有 refs 可能在大型仓库中开销大 → 通过配置限定 refs/pattern，与时间窗口结合早停。
- **Earliest/Late 条件缺失**：若时间范围内没有提交需要明确报错，提示用户扩大时间或 fetch 更新。
- **兼容性**：确保 `IncrementalSnapshotAssembler` 产出的结构能被 `ScanAppService` 现有逻辑接受（`DiffSummary`/`DiffFile`），减少上层改动。

## 结论
改造可在现有架构上平滑落地：通过新增 snapshot 管线和 facade，即可支持“全仓库、起止快照”式的增量扫描，同时保持与原有分支模式兼容，满足性能与迁移需求。***
