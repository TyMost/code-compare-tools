# 前后端改造计划

## 背景与目标
- 当前扫描/比对接口要求调用方每次显式传入 Oracle 与 Gauss 的仓库路径和分支信息，临时使用成本较高。
- 期望先在后端通过配置文件提供一组默认仓库/分支，前端调用时可只指定预设名称；未来再逐步过渡到前端完全管理多套仓库参数。
- 改造需兼顾短期落地速度与后续扩展性，避免临时方案成为技术债务。

## 整体策略
- 后端引入“预设（preset）”概念：通过 `application.yml` 配置多套仓库差异组合，对现有接口向下兼容。
- 前端优先支持选择/调用预设，逐步扩展到允许用户在界面内编辑或直接传入完整仓库参数。
- 采用两阶段交付：阶段一完成配置化默认值与预设调用；阶段二开放自定义参数及持久化能力。

## 后端改造方案

### 阶段一：配置化预设（立即执行）
1. **配置文件**  
   - 在 `application.yml` 中新增 `migratediff.presets` 列表，示例：  
     ```yaml
     migratediff:
       presets:
         - name: default-og
           source:
             code: o-g
             path: D:\Coding\code-compare-tools\examples\o
             branchFrom: refs/heads/o1
             branchTo: refs/heads/o2
           target:
             code: g
             path: D:\Coding\code-compare-tools\examples\g
             branchFrom: refs/heads/g1
             branchTo: refs/heads/g2
     ```
   - 预留拓展字段（`deltaType`、`includeWorkingTree`、`remoteName` 等），避免后续再改结构。
2. **属性绑定与领域模型**  
   - 新增 `ScanPresetProperties`（使用 `@ConfigurationProperties("migratediff")`）和相关数据类，将 YAML 映射为内存中的 `List<ScanPreset>`。
   - 提供查找、覆盖逻辑：根据 `preset.name` 返回默认的 Oracle/Gauss `DiffRequest`。
3. **DTO 与 Mapper 调整**  
   - 在 `ScanRequestDTO` 中添加可选字段 `presetName`；现有 `oracle`、`gauss` 字段改为 `@Valid @Nullable`，默认值由预设填充。
   - 更新 `ScanMapper.toInput`：若存在 `presetName`，先加载预设为基础，再用请求中显式提供的字段覆盖（支持部分覆盖）。
4. **控制器与响应**  
   - `ScanController` 继续沿用 `scanMapper`，无需额外分支逻辑；保持向后兼容（仍接受完整配置请求）。
   - 新增 `GET /api/scan/presets`（可选但推荐），返回预设列表供前端展示。
5. **验证与文档**  
   - 编写单元测试覆盖预设加载与字段覆盖逻辑。
   - 更新 `docs/backend/api/Migratediff-API-Manual.md`，增加 `presetName` 请求示例。

### 阶段二：前端驱动的配置（后续迭代）
1. 在后端实现 `RepoConfig` 的持久化（数据库或配置文件），`RepoController` 返回带 ID 的配置集合。
2. 允许 `ScanRequestDTO` 传入 `oracleConfigId`/`gaussConfigId`，后端查询后组装完整参数。
3. 对接 `SettingController` 持久化方案或新增配置管理接口，实现界面化增删改预设。

## 前端改造方案

### 阶段一：消费预设（立即执行）
1. **配置加载**  
   - 新增调用 `GET /api/scan/presets` 的初始化逻辑，将可用预设加载到前端状态管理。
   - 如果暂未提供该接口，可将预设名称写死为 `default-og`，与配置文件保持一致。
2. **扫描/比对请求**  
   - 触发扫描时默认发送 `{ "presetName": "default-og", "persistResult": true }`，必要时允许用户覆写个别分支字段。
   - 保持现有与后端字段一致，便于未来直接切换到“全参数模式”。
3. **界面提示**  
   - 在相关表单中展示当前激活的预设信息（源/目标仓库路径与分支），减少用户困惑。

### 阶段二：多预设与自定义（后续迭代）
1. 提供预设选择下拉框，并支持编辑/新增预设后调用后台配置接口。
2. 在 UI 中允许高级用户展开“自定义参数”面板，直接编辑仓库路径、分支、`deltaType` 等字段，与后端覆盖逻辑保持一致。
3. 若后端完成持久化，可新增 CRUD 页面管理 `RepoConfig`，并通过 ID 触发扫描。

## 验收与测试
- **后端**：针对预设名存在/不存在、字段覆盖、默认值缺失等情况编写单元测试；进行一次完整的 `/api/scan/full` 手工验证。
- **前端**：模拟用户选择预设并执行扫描，确认 API 请求体符合预期；在“自定义覆盖”场景下验证覆盖逻辑生效。
- **文档**：更新 API 文档与前端操作手册，确保团队成员理解预设与自定义参数的关系。

## 风险与注意事项
- 配置文件中的路径与分支需与实际仓库保持同步；建议结合环境变量或 profiles 管理不同环境的预设。
- 预设覆盖逻辑要明确优先级，避免请求与预设混用时产生意外结果。
- 阶段二涉及持久化与权限控制时，应提前设计配置变更流程，防止误配置影响生产环境。
